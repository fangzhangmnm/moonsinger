## 一、规矩（1 + 1）

1. **分工。** 小弟：侦察、实现、测试、守卫、文档（流程图 `20261109-pipelines.md` 跟改动同一个提交更新；仓 `CLAUDE.md` 的流水）、发开发版。统筹：这份施工单、ADR、设计稿；审 1a 的切线表和第三刀；回答第五节的问题。统筹不写代码，小弟不做设计决定。
2. **什么时候停下来问**（写在第五节，再给统筹发一条消息）：
   - 施工单和设计稿没写，而且答案会动到这四样之一：设计稿第 3.1 节的「谁不许知道什么」；歌的文件格式；点击 / 光标指向谱的地址；user 看得见的行为。
   - 守卫过不了、想放宽守卫。
   - 活比工单表写的大出一倍。
   - 别的（命名、文件怎么拆、内部数据结构、测试怎么写）自己定，在施工记录里记一行。
3. **接口形状。** 设计稿第 7 节是提案。字段名、参数形状可以自己调，调完回写第 7 节、施工记录里记一句。「谁不许知道什么」不能自己动。
4. **提交。** 两个会话共用这个目录：各自只提交自己改的文件，写明路径，不用 `git add -A`。这份施工单里，小弟写第五节的「问」、第六节、工单表的状态列；别的地方统筹写。
5. **测试和发版**照仓 `CLAUDE.md` 的分档；开发版照常发；正式版不碰；版本号一律 patch。
   - **测试分级，不要拖**（user 2026-11-11 夜：「可以想办法测试分级一下，不要太拖。开发的时候可以相对细致一点，开发完一块可以收成几个综合的对抗性测试」）。下面是统筹的读法：
     - 一刀没做完的时候：可以细。脚手架式的守卫（比如守卫 3 的几十份全量快照、每一小步的对照）尽管加。但细的不进「每改一下都跑」的那一档：那一档整套照旧 10 秒以内。细的放在「改完一小步 / 提交前」跑，只跑和这一步有关的。
     - 一刀做完、交付之前：收。把这一刀的细测试收成几条综合的对抗性测试长期留着。每条盖一大片、专门往不变量上撞（把每种写法用一遍的测试歌、真实密度的大歌、一串随机的编辑、边界情形）。其余的脚手架删掉，不长期留两份。
     - 收的时候守卫不许变薄：设计稿第 3.9 节的每一条守卫，收完之后仍然指得出是哪一条测试在守。
     - 不念旧：一刀做完收的时候，长期留的底本用分家之后的代码重新存。旧代码因为不好的办法带出来的误差（比如按 `行号 × 8192` 垫高度丢的浮点尾数）只在这一刀里当参照，不带进长期的底本，更不让新代码去复现（user 2026-11-11 夜：「本来就不用太念旧，如果旧的是因为用不好的办法导致的误差，我们为什么要新的代码复现？这样不是屎山吗」）。
     - 旧的输出不是金标准（user 2026-11-11 夜：「if our early graphics is ugly then it is no need to fix it as golden reference」）。底本只用来抓意外的改动，不证明旧的好看。和底本不一样时分三种：说不出为什么变了 = 查（可能是新弄坏的）；说得出原因、原因是旧办法的毛病 = 不复现，施工记录里记一行；看得见的不同（位置、大小、谁盖住谁）= 不为了和旧的一样改回去，截图记下来，交付时和样张一起经统筹给 user 看，好不好看由 user 判断。
     - 每刀的施工记录里记：收之前几条、跑多久；收之后几条、跑多久；每条不变量由哪条测试守。
     - 整套浏览器测试只在一刀交付时跑；小步之间按改了什么只跑那一区。
5½. **交给 user 看的样张 = 成品**（user 2026-11-11 夜，看了第四刀的三张裁过的图之后：「我看你给我的图都是一些裁的七零八碎的素材图，不是一张成品的稿子。」）。一律交 app 自己导出的 PDF，加每页一张整页的图（不裁、带页边、不拼成长条）。图标这类小东西照旧一张对照图。统筹转给 user 之前自己先看一眼：它在 iPad 上读起来是不是一份成品。
6. **消息。** 一刀做完、或者有事要问：先写进文件，再给统筹发一条消息（一句话 + 看哪一节）。每刀做完把要记的都写进文件再停，这样两边随时可以压缩或重开。
7. **不拿「改动小」当理由**（家规）。想加一个施工单没写的口子时，先答两句：它以后会长成什么；它反映了什么结构。答不出来就写进第五节问。

### 4 简谱单声部（统筹补的细则，2026-11-11）

目标：一首单声部的歌（人声旋律 + 歌词）切到简谱，能看、能写、能印。依据 = UX 稿第 3–6、8–9 节，设计稿第 3.3、3.8 节。

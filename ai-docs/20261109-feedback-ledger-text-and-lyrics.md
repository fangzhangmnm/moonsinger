## 二、交给 Fable 统筹（还没动）

1. **谱头面板「这位的谱」四项的归属**：「staves的逻辑能不能收到clef里面，或者后面四个选项应该没有，收到前面的per sheet而不是跟着歌手。只有shared staves有」「可以高音低音grand用户每个sheet选」「一开始是auto，auto也会自动变成grand，你看一下是什么规则」。
   现状：谱表（单 / 大谱表）、默认谱号、自动八度线、合租都存在歌手身上管整首；面板上半已有按纸的谱号 / 调号 / 拍号 / 速度。
   现在的「自动」规则：单人的自动谱号永不选大谱表（在高音 / 低音 / 8vb / 8va / 15ma / 低音 8vb 里挑加线最少的，翻纸有惯性，加自动八度线）；合租叠起来的那一行在「主人设了大谱表」或「各位的家分两边且大谱表读起来更省（`clef.ts wantsGrand`：单谱号的加线 + 八度线成本 vs 大谱表每音多 0.5）」时自动双手谱。
   要定：按纸存在哪（可选字段 / 新 token，格式红线区）、旧歌怎么读、合租的家谱怎么跟着纸变、单人「自动」要不要也能选到大谱表。
2. **文字排版引擎收成一个深模块、窄接口**（「到时候让fable把文字排版引擎审核的时候写个计划书让opus做收成一个深模块窄接口」）：样式表已收；歌词让路（`solveLyrics` / `fitLyrics` / `lyricBlockSx`）、量字（`measureLyric` 注入 + 各处按字号比例换算，现在由 engrave 的 `RS` / `TR` / `mw` 收着）、连字符、覆盖层基线还散在 engrave / score-view / score-overlay。写计划书交 Opus 施工。
3. **性能**（「到时候记得让 Fable 看一下这个性能，不要太难看」「让fable看一下排版引擎是整个曲段重拍还是修一行，可以优化一下。算法的优化也给fable」）：
   - 歌词让路：800 个十六分音符全带英文，engrave ≈ 40 ms，不让路的排法 ≈ 20 ms（node、粗估量字）；普通歌轻得多。时间主要在「挤的那一串」的二分（先缝后字）和放宽。
   - 排版粒度：现在每改一下整张纸（本段视图）/ 整首（全部视图）都重排；排版在 worker 里、有缓存（谱没变不重排），但没有「只重排一行」。
4. **紧凑档的缝底线**：样张里极端挤的英文（每个十六分音符一个音节），缝收到 0.2 线间距时个别词之间只剩一道很细的缝（「aup」「howI」）。0.2 是 AI 定的数，要不要按档 / 按字号定，跟着第 2 条一起想。

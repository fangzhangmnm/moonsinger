## 1. user 交代的（原话，2026-10-05）

> 「下一个session可以开始内耗五线谱和简谱和钢琴格的事情了，顺便提前排一下，和ora一样尽量用已有的开源格式。这样backward compatibility的概率小，然后backward compatibility按照catsup的范式，每个模块有一个自己的版本号拍子。然后有一个独立的迁移模块，尽可能瘦」

拆开：
1. **内耗记谱界面**：五线谱、简谱、钢琴格（piano roll）三选几、怎么共存。是讨论，不是开工（讨论≠授权，见家族记忆）。
2. **存档格式尽量用现成的开源格式**，像 WeebPaint 用 OpenRaster（.ora）那样：主体是标准格式，我们的东西是挂上去的扩展。
3. **向后兼容按 CatsUp 的范式**：每个模块（子结构）自己的版本号；一个独立的迁移模块，尽可能瘦。

## 2. 要照抄的两个先例（读代码，别读二手描述）

- **CatsUp 持久化立宪**（条文 SSoT = CatsUp `ai-docs/20260919-persistence-data-contract.md` §7 + CatsUp `CLAUDE.md`「持久化立宪」条；代码 `src/format/`、`src/format/migrate/`）：
  - 每个自定义子结构独立 `version` 整数，互不牵连；
  - 迁移 = 纯函数，全住 `src/format/migrate/<扩展>/v<N>-to-v<N+1>.ts`，读取时链式升级，写入只写当前版；
  - 每发一版冻结样本进 `test/fixtures/format/<扩展>/v<N>/`，迁移测试 = 旧样本 → 当前 → 与 golden 一致；
  - 老文件永远能开，只拒开比 app 新的；读到旧版只在内存里升级，用户真保存才写新版；
  - **标准追随**：标准本身覆盖了某块数据时，写入改用标准形，读取保留旧扩展的读法（一条迁移），不写双份。
- **WeebPaint 的 .ora**（`src/backend/ora.ts`、`src/backend/ora-stack-xml.ts`、`src/backend/format/layout.ts`）：OpenRaster = zip + `stack.xml` + 每层 PNG；WeebPaint 的东西作为额外 entry / 属性挂上去。WeebPaint 的纪律：「每次动 .ora 内部布局…必须严格上报 user，并附一张具体文件的完整目录表」（WeebPaint `CLAUDE.md`）。

## 3. 候选的现成格式（AI 凭记忆列的，**一条都没核**，下个 session 先核）

| 格式 | 是什么 | 对 MoonSinger 的意义（AI 读法） |
|---|---|---|
| **MusicXML（.musicxml / 压缩 .mxl）** | W3C 社区组的乐谱交换格式；.mxl = zip + `META-INF/container.xml` | 最像 .ora 的位置：zip 容器、业界通用（MuseScore 能开）、自带歌词（`<lyric>` 可多段，`number` 区分第几段）。容器里能否放我们的扩展文件、简谱有没有官方表示：未核 |
| **OpenUtau USTX** | OpenUtau 的工程文件（YAML，开源 MIT 软件的格式） | 「歌手优先」的数据模型：音符带歌词，表情是曲线，曲线名正好是 §8 那套（音量、气息、张力、实声、男女声感…）。和 §8「乐器复用歌手的旋钮命名」最贴 |
| **Standard MIDI File** | 最老的通用格式 | 音符、速度、歌词事件、控制曲线；没有记谱语义（升降号写法、连音线、简谱） |
| **ABC 记谱法** | 纯文本 | user 2024-10 ~ 2025-01 自己用 ABC 扒谱写歌走通过一轮 |
| **LilyPond** | 纯文本排版语言 | 今天「うさぎ」的旋律就是从维基的 LilyPond 源码取的；工具链重 |
| **jianpu-ly 等简谱文本** | 简谱文本格式（10-05 peek：jianpu-ly Apache-2.0、simple-notation MIT、musje 许可矛盾） | 简谱更像「视图」而不是存档格式 |
| MEI / DiffSinger .ds / VOCALOID .vpr / Synthesizer V .svp | 学术 XML / 音素级 JSON / 商业私有 | 大概率只作导入参考 |

一个 AI 的猜想（待内耗）：**存档主体 = MusicXML（.mxl 容器），月读的旋钮曲线、贴纸图等作为容器里的扩展文件，每个扩展一个版本号**；或者反过来，以 USTX 为主体。哪个当主体，取决于第 4 节里「音高存什么」「旋钮挂在哪」的答案。

## 4. 内耗时要回答的问题（从今天的对话里攒的）

1. **三种界面谁是视图、谁是数据**：简谱 / 五线谱 / 钢琴格是同一份数据的三种看法，还是各有偏重？user 10-05：「五线谱和钢琴窗我们可能还会摇摆很久。儿歌也只是一个可选项」；「说不定简谱和数字键盘有神效。不过核心设备还是ipad mini」；peek：诺基亚作曲器 1–7 是固定调（1 = C），简谱是首调。
2. **音高存绝对音高还是「几级音 + 调」**：首调让转调只改一处（今天 Lab 里 `--transpose` 就是这个需求）；08-19 的旧提案「离散时值不进数据结构，纯 UX」是否也适用于音高。
3. **一个音符的最小字段**：音高、时长、**音节位**（唱的是歌词，奏的是起音音节，§8）、表情曲线挂在音符上还是挂在时间轴上。Lab 的 `score.mjs` / `score-dango.mjs` 是一个能用的最小原型：`{ kana, notes: [[midi, 八分音符数]…], rest, moras }`。
4. **多段歌词与角色**：《小兔子乖乖》样张——一条旋律多段词、每段标「谁在唱」（颠覆文档 §6.3）。
5. **月读的旋钮命名**（§8）：表情曲线的名字用她的（气息、张力、实声、嘴张多大、男女声感、辅音长短…），乐器来复用。Lab `sing.mjs` 里已有 `OPT.breath` / `OPT.level` 两个实做。
6. **HSV 与音符大小**：user「有电脑屏幕之后hsv确实可以比专业符号更有用。包括音符的大小」——表情的可视化通道。
7. **贴纸**：乐谱里一张贴纸级别的图（颠覆文档 §3）；若用月读立绘，角色许可（§10）。
8. **中文歌词**：倒字（旋律走向与声调相反）是否要提示（10-05 聊到，未定）。

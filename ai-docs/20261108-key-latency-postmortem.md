# 键盘延迟：事后调查与反省

> created 2026-11-08 by Claude Fable 5.1
> as-of v0.16.31 / 2026-11-08（写这份时，「切后台回来没声音」的原因还没找到，见 §6；v0.16.31 的改动见文末「后记」）
> 依据：这次对话的完整记录（压缩前的也读了）、user 当晚发来的三份诊断日志、仓里的提交历史。时间都是 user 设备上的当地时间。
> 文中「黑匣子」= 设置里的诊断日志；「声音设备」= 系统替网页放声音的那一套；「起来」= 它从停着到开始出声。

## 0. 一页结论

**病是什么（已在 user 的 iPad 上证实）**

iPad 上声音设备每次起来，有时「起得脏」：app 告诉系统「开始放」之后，设备过一会儿才真的开始要声音，这段时间里已经多算出一截声音（量到过 224 毫秒、约 590 毫秒）。多算的这一截排着队播，之后按的每个音都排在它后面，所以每个音都晚这么多，一直到下一次声音设备重起。起得干净的那几次（多算 1 毫秒）完全不晚。

app 自己量的几段时间（手指按下 → 程序接到 → 把音交出去）、音频时钟、浏览器报的输出延迟，在起得脏的时候全都正常。所以「数字都正常、听着却晚半秒」。

**不是什么（都有证据，见 §4）**

不是最近哪一版改坏的；不是键盘代码或界面卡住；不是歌太大、写久了积累的；不是某一种乐器；重启 iPad、还原出厂、重装、升级系统都不管用，因为它们都只是让声音设备再起一次，起得脏不脏是另一回事。

**回答 user 的问题**

user 22:10 的原话（语音转写）：「其实是我们这个项目逆向之初就一直都有的，只是我一直在写歌才慢慢的积累下来的，还是说是什么情况？就是说，并不是这几次改改换的。」我把「逆向之初」读作「立项之初」，「改改换的」读作「改坏的」。

- 「不是这几次改坏的」：对。
- 「一开始就有」：对，弱点从实时出声那一版（10 月 9 日，v0.9.1）起就在——app 把声音设备叫起来之后，从来不检查它起得干不干净。之前记过账的那件事多半是同一个病——user 11 月 7 日：「声音比高亮慢一拍。这个还没解决，不过确实是切后台触发的，重启能好。」
- 「写歌慢慢积累下来的」：没有证据支持。这个病是每次声音设备起来各算各的，新歌、即兴、不登录都会有，和歌的内容、用了多久无关。
- **没解释的**：以前连着写了几个星期都没事，为什么 11 月 8 日下午连着不行。见 §6。

**现在的状态**

v0.16.30（开发版）：声音设备每次起来都量一次，多算超过 30 毫秒就清掉（把声音暂停再恢复），永远开着；弹的中途排队又涨上去，就等手离开键盘的空当清。清这个动作在 iPad 上证实过一次（224 → 1 毫秒，user「延迟好了很多」）。别的都没在 iPad 上证实，逐条写在 §5。

## 2. 病理：三份黑匣子里的数

**第一份（v0.16.25，21:02 导出）**
第一次按键后，程序这一侧是干净的：按键排队 20 毫秒，处理 2 毫秒，界面没卡。同一时刻声音上下文写着「在跑」，音频时钟却整整一秒没动，然后两步跳了 344 和 243 毫秒（合计约 590）。当时我只读出了「设备起得慢、第一个音晚一秒」，没读出那两步跳意味着什么。

**第二份（v0.16.27，21:54 导出）**
探针每一项都正常（排队 23、处理 1、声音块平常 16 / 最长 40 毫秒），user 却听到每个音晚 300 到 700 毫秒。这个矛盾是转折点：慢在探针量不到的地方。回头看第一份里的「一口气跳 590 毫秒」——时钟一瞬间多走半秒，就是一瞬间多算了半秒声音，它们得排队播完。

**第三份（v0.16.28，22:06 导出）**
这一版加了量排队的表和自动清，留了一个关掉它的开关（user 提的做法）。三次打开 app：

- 22:04:50 起来：多算 224 毫秒 → 自动清 → 再量 1 毫秒。user：「延迟好了很多」。
- 22:04:56 起来：多算 1 毫秒，没东西可清。user 在这一次里关了开关，「感觉延迟没有变」。
- 22:06:04 起来（开关关着）：多算 1 毫秒。user：「延迟完全好了」。

所以好不好不取决于开关，取决于这一次起得脏不脏；开关只在起得脏的那次有用。

**顺带对上的两件旧事**（推断，没逐条证实）

- 「歌播放的时候完全没有延迟」：放歌时每个音的时刻是提前排好的，整体晚半秒，耳朵听不出来；按键是实时的，晚半秒马上能感觉到。
- 声音比高亮慢（user 10 月 10 日「ipad后台唤起后音频和动画错位」，11 月 7 日那句见 §0）：高亮画在浏览器报的「扬声器放到哪了」，而浏览器不报排队的这一截，所以声音比高亮晚的正好是排队的量。

## 4. 每个猜测的账

**被推翻的**

- **Opus 改键盘把性能改差了 / 界面刷新卡住主线程**（user，15:35、16:23、21:23）
  探针在 iPad 上量到：按键排队 14–25 毫秒、处理 1–2 毫秒、界面没有长停顿。键盘这条路是干净的。
- **独立窗才慢，浏览器标签不慢**（Fable 17:21，依据是 user 16:26 的一次观察）
  21:20 user：「网页版好像也不行」。那一次不慢，现在看只是那一次起得干净。

  user 自己推翻：正式版 v0.15.5 登录后也慢，开发版退回 v0.16.14 也慢。另有一条硬证据：声音线程实际加载的那个文件，从正式版到当晚的开发版是同一个文件。
- **v0.16.26 的「重启声音」把第一个音拖到 6.7 秒**（Fable 21:50）
  黑匣子里那十秒声音一直是「被系统打断」的状态，那段代码只在「在跑」时动手。Fable 21:58 更正。
- **这台设备 16:27 才第一次登录网盘，所以今天才出事**（Fable 21:42）
  user 纠正：一直是登录着写的，那一下是重装之后重新登录。对话记录能对上：16:26–16:28 user 正在重装。

  改掉之后没有变化。

- **和有没有登录网盘有关**（user 21:41）

## 6. 还没解释的

1. **为什么 11 月 8 日下午连着起得脏。** 这是整件事里最大的空白。那天这台 iPad 有两条状态不好的迹象：21:15 小月相的引擎报过一次内存不够；黑匣子里至少三次（21:43、22:04、22:06）app 刚打开，声音上下文一建出来就被系统标成「被打断」。这两条是迹象，不是原因。量到的两个数据点是「设备起得越慢，多算得越多」（等 0.3 秒多算 224，等 1 秒多算 590），只有两个点。
2. **登录和它的关系。** 见 §4。
3. **切后台回来直接没声音**（v0.16.28 / 29）。v0.16.27 的黑匣子里，回来 60 毫秒内声音设备就自己起来了，有声音；没声音是之后才有的。嫌疑是回来之后那一次清、叫不醒接着叫、保持醒着的信号，三样里是哪一样没读出来。v0.16.30 撤了一样、给另一样加了护栏和记账。**有可能没修好。**
4. **第二次打开时「快速弹还慢一点点」**，量到的排队却是 1 毫秒。那一次探针的汇总没来得及写进黑匣子。
5. **「四十多毫秒」是横幅上的哪一个数。** v0.16.29 起每段按键的汇总都带名字写进黑匣子，下一份日志能看出来。
6. **声音被打断十秒、第一次按键叫不醒**（21:43 那一次）。
7. **两个键同时按有一个不认**，后来又能认了。单独记了账，排在延迟后面。

## 7. 反省

**AI 这一侧做错的**

1. **在复现不了的电脑上测了一下午。** 电脑上声音设备起得干净（多算 3–7 毫秒），怎么量都是好的。Opus 量写谱那条路、Fable 回溯版本、反复跑八分钟的全套测试，都在这台电脑上，user 在旁边等。user 21:21 说的那句是对的。
2. **把一次观察写成了「查明」。** 17:21 的结论只有 user「标签页不慢」那一次观察撑着，却写成了定论，然后去做别的。user 三个半小时后才带着黑匣子把它拉回来，这段时间他写不了歌。
3. **没证实的修法出了货，一次三处。** v0.16.26 的三处改动哪一处都没在 iPad 上验过，其中一处下一版就撤，撤的理由还是错的。同一晚对同一件事下了三次结论，改口两次。
4. **怪系统、怪版本。** 第一轮怪系统的独立窗；user 说「别怪系统」之后转去逐版本找。两条都是 user 用自己的对照掐掉的，不是我查出来的。
5. **读日志读出了日志里没有的东西。** 「今天才第一次登录」是我从一行「登录跳转」脑补的。
6. **第一份黑匣子里已经有答案，我没看出来。**「停一秒，然后跳 344 + 243」当时就在那里。我只把它读成「第一个音晚一秒」，一个小时后才明白那两步跳的意思。
7. **没问清就动了线。** 「四十多毫秒」我当成了排队那一项，改了门槛；user 随后说他不知道是哪个数。
8. **当晚的补丁带出了新毛病**（回来没声音），写这份时还没找到原因。

**起作用的做法**

1. **把数字放到 user 的设备上量**（v0.16.23 的探针和黑匣子）。之后每一步进展都来自这三份日志。
2. **盯住矛盾**：数字正常、听着却晚，说明要找的东西在量不到的地方。
3. **修法默认开，留一个回到旧行为的开关，每一步记账**。这是 user 提的，一轮就定了案。
4. **user 的对照实验**（正式版对开发版、登录对不登录、标签页对独立窗）每一个都比我的回溯快，而且是在出问题的那台设备上做的。

**user 问的：「我一开始的判断也不对」**

- 不对的：键盘 / 主线程被改坏了；是开发版的代码改错了。
- 部分对的：和登录有关（相关是真的，因果没找到）。
- 对的：「歌播放没延迟，是键盘的问题」这条观察后来正好能用排队解释；不该怪系统、不该在复现不了的电脑上测；带开关验证；「切后台回来慢可能是同一种病」。

## 8. 以后怎么做

- **只在 user 设备上出的毛病**：读代码推理，在设备上量；不在复现不了的电脑上反复测；不怪系统。（当晚已记进家族记忆。）
- **「查明」两个字只在有设备上的证据时才写**，否则写「推断」，并说清靠的是哪一次观察。
- **碰声音设备的改动一版只动一样**，带黑匣子记账，说明证实没有。
- **没证实的修法**要么不出货，要么像 v0.16.28 那样带对照开关。
- **跑测试守分级**：平时只跑相关的；当晚已把六份慢的归成专项，默认不跑。

**接下来的事**

1. 回来没声音：等 user 的黑匣子。v0.16.30 的日志会写明回来时声音的状态、清没清、清完起没起来、按键那一刻时钟走没走。
2. 用几天的黑匣子攒「设备起了多久、多算了多少」，看起得脏有没有规律（§6 第 1 条）。
3. 两个键同时按不认 + 其他手感优化（延迟之后做）。
4. 复核「声音比高亮慢一拍」是不是随这次一起好了。

## 附：黑匣子里这几行怎么读

- `start burst (running): device start took ≈ N ms, rendered ahead ≈ M ms`：声音设备起来了一次，等了 N 毫秒才真开始，多算了 M 毫秒。M 就是之后每个音要晚的量。括号里是这次为什么起来：`created` 第一次、`running` 被系统停过又起、`flush` 我们自己清出来的、`visible` 回前台时发现时钟没走。
- `flush (auto | idle | tap; queued ≈ N ms)`：清了一次。auto = 起来时量到多算；idle = 手离开键盘的空当；tap = 人点了横幅那一行。
- `flush left ctx … for 1 s → waking; auto flush off this session`：清完没起来，接着叫醒，这次打开不再自动清。
- `state A → B`：声音上下文换了状态。`interrupted` = 被系统打断着。
- `key pressed while ctx …` / `key pressed while clock frozen …`：按键那一刻声音不在跑 / 写着在跑但时钟没走。这两种情况这个键都不会按时响。
- `session: N keys, queue …, to sound …, audio step …, queued …`：一段按键的汇总，每个数带名字。

## 后记（v0.16.31，同一晚）

v0.16.30 上线后 user 的反馈：「现在是响应延迟非常的顺手，非常的快。」同时报了一个新问题：埙松手的一瞬间有静电似的杂音。

- **我第一反应是错的**：以为是这一版加的「空当里清」掐到了尾音，差点把清的做法整个退回去。user 接着给了三条观察（笛子没有、埙有；松手那一瞬间就有；播放时也有），都指向乐器自己而不是清。
- **这个在电脑上能复现**，因为合成器是同一份确定性代码：它每 64 个采样取一次音量，收音快的音色（陶笛 80 毫秒）出来就是一级一级的台阶。这是 10 月接进这个合成器时就有的，和当晚的改动无关。修法是让音量在这 64 个采样里平滑过渡；735 种按法里超标的从 603 种变成 0 种。
- **顺带改了清的规则**，这条是读代码读出来的隐患，不是 user 报的：v0.16.30 松手 0.6 秒后就可能清，尾音长的乐器会被硬掐。现在分两档——起来时多算超过 120 毫秒的当场清（证实过的那一档）；30 到 120 毫秒的等「确认没有音在响」才清。
- 和 §7 第 1 条对照：这次没有在电脑上瞎测，是因为先确认了它在电脑上能复现。分清「能不能在这台机器上复现」是第一步。
